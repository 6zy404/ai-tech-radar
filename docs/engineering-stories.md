## 一、工作台单页渲染 125 秒并阻塞整个服务器

**概要**：一个未缓存的派生视图在每次渲染中被重复构建数百次，导致单页渲染约 125 秒，
并因 Node 单线程阻塞所有其他请求。加入两段式缓存键后降至 280 ms（448 倍）。第一版
正确性验证缺少对照组，结论无效，已替换。

### 症状

对工作台页面截图时超时，同一时刻所有公开页面也超时。Node 是单线程的，一次同步的
CPU 密集渲染会阻塞整个进程，而不只是它自己那条路由。

### 定位

分别测冷启动与热请求，排除 dev server 首次编译的影响：

| 路由                    | 冷      | 热      |
| ----------------------- | ------- | ------- |
| `/workspace`            | 124.7 s | 125.4 s |
| `/workspace/candidates` | —       | 62.7 s  |
| `/workspace/operations` | —       | > 90 s  |

冷热几乎相同，说明耗时来自每次渲染都会执行的逻辑，而不是编译。

根因是 `getCandidateWorkflowData` 没有缓存：每次调用都要解析约 3.3 MB 的 JSON（候选
快照单个文件 2.7 MB），再对全部候选做两两去重，约 200 ms 一次。
`getImportedCandidateById`、`getDuplicateGroups`、`getDuplicateGroupCandidates` 都
经过它，因此一次转换就绪性检查会重建 2 到 4 次，运维聚合则对每条候选各调用一次。

在运行中的服务器上插桩：共 **2,075 次调用，累计 416 秒**；`/workspace` 单次渲染占
125 秒、约 620 次。

### 修复

对源读取做记忆化，缓存键由两部分组成：

- **进程内写入计数器**：捕获本进程的写入
- **文件指纹**（`statSync`）：捕获其他进程的写入。`tasks:run-once` 以独立进程写同一批
  文件，只用计数器会漏掉这部分

结果：**125,413 ms → 280 ms（448 倍）**。14 条工作台路由重测，最慢 1,483 ms。

### 正确性验证

第一版验证方法：写入前后各抓一次页面，比较哈希；哈希不同即认为缓存正确失效。

加入对照组（两次都不写入）后，哈希**同样不同**——页面中渲染了实时时间戳。因此该方法
在任何情况下都会报告「有差异」，不能证明缓存失效，结论作废。

改为比较稳定的状态计数，并先确认对照组连续两次完全一致，再做三项测试：

1. 经 API 写入：`37/95 → 38/94 → 37/95`
2. 从**另一个进程**写入：同样 `37/95 → 38/94 → 37/95`
3. **反向对照**：将缓存键固定为常量，写入**不会**被反映，全程 `37/95`

第 3 项说明这个检查在实现错误时确实会失败。

### 防止回归

这个问题是随数据量增长逐渐出现的，而不是某次提交引入的，因此补充了 6 条测试，并用
三种注入分别确认每条测试只拦截对应的问题：

- 缓存键写死为常量 → 2 条失效测试失败
- 保留计数器、去掉文件指纹 → 只有「其他进程写入」那条失败
- 跳过记忆化 → 2 条「只构建一次」测试失败

### 取舍说明

- **为什么不换数据库**：问题不在存储速度，而在同一份数据在一次渲染中被重复解析数百次。
  换数据库会掩盖这个问题，而不会消除它。
- **为什么缓存键需要两部分**：去掉文件指纹后只有「其他进程写入」的测试失败，而那个
  进程就是每天运行的定时任务。
- **缓存的对象**：缓存的是源读取结果，不是返回的数组；每个 getter 仍会构建并排序一份
  新数组，调用方之间不会互相修改列表。

> 出处：[`docs/next-task.md`](next-task.md) 2026-08-17 更新的第 ⑮、⑲ 段。

## 二、五个公开页面在生产构建中被永久静态化

**概要**：五个公开页面缺少 `force-dynamic` 声明，生产构建会将其预渲染且永不重新生成，
导致编辑发布的内容在这些页面上不更新。这是正确性问题：站内不同页面对同一数据给出
不一致的结果。已通过真实数据探针确认，并在修复后用同一探针验证。

### 发现

在搭建生产环境对照时发现：`/skills`、`/skills/[slug]`、`/knowledge`、
`/knowledge/[slug]`、`/network` 是仅有的五个没有 `export const dynamic = "force-dynamic"`
的公开页面。`next build` 会预渲染它们，且 `initialRevalidateSeconds` 为 `false`，
即永不重新生成。41 条预渲染路由中有 38 条来自这五个页面。

### 验证方法

构建清单只反映配置，不能证明运行时行为，因此做了一次判别实验：让生产服务器读取
`config/` 的**副本**（不写入线上存储），在副本中给一条已发布技能的标题加入标记字符串，
然后检查四个页面：

| 页面                | 命中标记 |
| ------------------- | -------- |
| `/workspace/skills` | 有       |
| `/skills`           | 0        |
| `/skills/[slug]`    | 0        |
| `/network`          | 0        |

同一进程、同一份数据，工作台页面已更新而三个公开页面没有，排除了「数据未变化」的解释。

### 影响

`/search` 是动态渲染的，能搜到修改后的标题，但点进去的详情页仍是旧内容——站内结果
互相矛盾。技能 / 知识的工作台编辑功能正是为运行时新建和发布条目而设计的，在生产构建中
这些发布不会出现在对应页面上。

### 修复与代价

该修复改变部署行为，因此先测量代价再决定：加入 `force-dynamic` 后，生产环境响应时间
为 **10–47 ms**（`/skills` 12 ms、`/knowledge` 11 ms、`/network` 39 ms、技能详情 47 ms），
预渲染路由 **41 → 3**（剩余为 favicon、icon 与 404 页）。

用同一份带标记的副本复测，三个公开页面的命中数从 **0 / 0 / 0** 变为 **2 / 4 / 3**，
与工作台一致；再用真实存储做对照，内容正常，未知 slug 仍返回 404。

### 附带改动

1. 删除两个 `generateStaticParams`。`force-dynamic` 下它们已不起作用，保留会误导读者
   以为页面是预渲染的，并且在将来移除 `dynamic` 声明时会让页面重新静态化。随之产生的
   两个未使用 import 由 lint 发现。
2. `validate:deployment` 新增检查：`src/app` 下每个 `page.tsx` 必须显式声明渲染模式
   （当前零例外）。通过移除某个页面的声明确认检查会失败，并先确认注入确实修改了文件。

### 取舍说明

- **为什么之前没有发现**：本地 `next dev` 始终动态渲染，该问题只存在于生产构建中，而
  此前没有运行过生产构建。
- **为什么不用 ISR（revalidate）**：这些页面的数据来自本地 JSON，写入由编辑操作触发，
  没有自然的重验证周期；动态渲染实测仅 10–47 ms，不值得为此引入内容陈旧的时间窗。

> 出处：[`CHANGELOG.md`](../CHANGELOG.md) → “Five public pages would have shipped
> frozen at build time”。

## 三、最慢公开路由的耗时主要来自开发模式

**概要**：一次全站计时扫描将 `/technologies` 报告为最慢的公开路由（445 ms）。排查
结果是该数字来自 `next dev`，生产环境为 16 ms，最终无代码改动。这次排查得到了一个
可复用的判断方法：用 dev / prod 耗时倍率区分真实开销与开发模式开销。

### 前提问题

扫描的计算本身无误，但所有数字都来自开发模式，而开发模式的开销与生产开销不成比例。

### 归因

临时加入 `renderLimit` 参数：只渲染 63 张卡片中的 N 张，但 props 仍序列化全部 63 条，
使载荷保持不变，只有渲染量变化。

| 渲染卡数 | 耗时   |
| -------- | ------ |
| 0        | 72 ms  |
| 16       | 163 ms |
| 32       | 271 ms |
| 48       | 377 ms |
| 63       | 436 ms |

呈线性关系，斜率约 **5.8 ms / 张**。436 ms 中约 364 ms 来自逐卡 React 渲染，数据加载与
475 KB 载荷约占 72 ms。（先确认参数生效：limit=0 渲染 0 张，limit=63 渲染 63 张。）

生产环境中同一斜率为 **0.11 ms / 张**，小 53 倍；整条路由 **16 ms**。两边卡片数、载荷
相同，且都是 `force-dynamic`，差异只来自运行模式。

### 排除的另一个嫌疑

`UnbreakableTitle` 在逐卡调用的辅助函数中执行 `new Intl.Segmenter("zh-CN")`，形态与
同周修复的两个性能问题相同。用真实标题做微基准：**构造一次 9.3 µs，63 张卡合计
0.5 ms**，不值得缓存。代码形态相似不代表开销量级相同，修改前先测量。

### 方法：dev / prod 倍率

测量 20 条按请求渲染的路由：

| 路由                    | dev → prod   | 倍率  |
| ----------------------- | ------------ | ----- |
| `/workspace`            | 189 → 107 ms | 1.8×  |
| `/workspace/operations` | 202 → 90 ms  | 2.2×  |
| `/feed.xml`             | —            | 1.8×  |
| `/workspace/sources`    | —            | 19.6× |
| `/technologies`         | 445 → 16 ms  | 24.7× |

倍率低，说明耗时来自真实工作（文件读取、解析、派生计算），值得优化；倍率高，说明
耗时主要来自开发模式下的组件渲染。

配套注意事项：

- 生产对照应构建到独立的 `distDir`。`next build` 与 `next dev` 共用 `.next`，对正在
  运行的 dev server 执行构建会使其进入异常状态。
- 预渲染路由的生产耗时是返回静态文件，不能与动态渲染耗时比较。
- 拆分渲染成本时要固定载荷，否则渲染与序列化同时变化，无法分别归因。

### 取舍说明

- **无代码改动的排查是否有价值**：它关闭了一项待办，并避免后续基于开发模式数字做
  无效优化。可复现的负结果同样是结论。
- **生产环境是否有慢路由**：最慢的公开路由为 32 ms，全站最慢为 126 ms，即第一节修过的
  那条路由；其 6.1× 的倍率表明剩余开销来自真实工作。

> 出处：[`CHANGELOG.md`](../CHANGELOG.md) → “The slowest public route was the dev
> server measuring itself”。

## 共同的做法

三次排查中，先出问题的都是测量方法，而不是被测代码：

- 第一节：页面中含时间戳，哈希比较在任何情况下都会报告差异。
- 第二节：构建清单反映的是配置，不是运行时行为。
- 第三节：开发模式的耗时不能代表生产环境。

由此形成的做法已写入 [`AGENTS.md`](../AGENTS.md) 的验证规则：**在采信一个检查的通过
结果之前，先注入一个缺陷，确认它会失败。** 编辑轮使用的八个正文检测器（引用块、竖线
表格、ASCII 引号、弯引号、纯文本字段中的标记、用户名形式的发布方、无法被解析的 `**`、
落单的反引号）都按这种方式逐个验证过。
