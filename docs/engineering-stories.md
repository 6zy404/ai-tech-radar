# 三个可讲的工程故事

这份文档是从 [`CHANGELOG.md`](../CHANGELOG.md) 和 [`docs/next-task.md`](next-task.md)
里提炼出来的，面向面试口述，不是开发文档。

三个故事共用一条主线：**我怎么知道我是对的。** 它们都不是「我实现了某个功能」，
而是「我做了一次测量，而那次测量本身先出了错」。这是它们值得讲的原因——每一个
里面都有一次自我推翻。

原始记录的位置写在每节末尾，方便追溯核对。

## 故事一：工作台把整个站堵死了 193 秒，而我的第一个正确性证明被自己扔掉了

**一句话**：一个没有缓存的派生视图让单页渲染耗时 125 秒并阻塞整个服务器，修完是
448 倍；但更值得讲的是，我用来证明「修复没有破坏正确性」的第一个方法是无效的，
是控制组把它揭穿的。

### 症状

给工作台页面截图时超时了。而同一时刻**所有公开页面也一起超时**——这是第一个线索：
Node 是单线程的，一次同步的 CPU 密集渲染会堵住整台服务器，不只是它自己那条路由。

### 定位

先冷热各测一次，排除「dev server 首次编译」这个常见的假象：

| 路由                    | 冷      | 热      |
| ----------------------- | ------- | ------- |
| `/workspace`            | 124.7 s | 125.4 s |
| `/workspace/candidates` | —       | 62.7 s  |
| `/workspace/operations` | —       | > 90 s  |

冷热几乎相同，所以不是编译，是每次渲染都在做的事。

根因是一个**没有缓存的函数**：`getCandidateWorkflowData` 每次调用都要解析约 3.3 MB
的 JSON（单个候选快照就 2.7 MB），再对全部候选跑一遍两两去重，约 200 ms 一次。而
`getImportedCandidateById`、`getDuplicateGroups`、`getDuplicateGroupCandidates`
**全都走它**——于是一次转换就绪性检查要重建 2 到 4 遍，而运维聚合是**每条候选调一次**。

在真实服务器上插桩确认：**2,075 次调用，累计 416 秒**；`/workspace` 单次渲染占
125 秒 / 约 620 次。

### 修复

两段式 key 的记忆化：

- **进程内写计数器**——抓本进程自己的写入
- **文件指纹**（`statSync`）——抓**另一个进程**的写入，因为 `tasks:run-once` 是独立
  进程在写同一批文件

结果：**125,413 ms → 280 ms，448 倍**。14 条工作台路由重跑，最慢 1,483 ms。

### 关键转折（这才是面试要讲的部分）

我的**第一个正确性证明是无效的，而且我差点就信了**。

方法是：写入前后各抓一次页面，比对哈希，有差异就说明缓存正确失效了。跑出来确实有
差异，看起来成立。

但我加了一个控制组：**两次都不写入**，再比对一次。结果两次哈希**也不同**——因为
页面里渲染了实时时间戳。也就是说，那个「有差异」什么都没证明，它在任何情况下都会
有差异。

换成稳定的状态计数（控制组先确认连续两次完全一致），然后三条实测：

1. 经 API 写入：`37/95 → 38/94 → 37/95` ✓
2. **从另一个进程**写入：同样 `37/95 → 38/94 → 37/95` ✓
3. **反向对照**：把 cache key 强制成常数，写入**不被反映**，全程 `37/95` ✓

第 3 条是最重要的——它证明这个检查**确实会失败**。一个永远通过的检查不是检查。

### 后续：让它不会再长回来

这个缺陷不是被写进去的，是**随数据慢慢长出来的**——注释拦不住第二次。所以补了 6 条
测试，并用三种注入验证每条只打中它该打中的：

- cache key 写死常量 → 2 条失效测试挂
- **只留计数器、去掉文件指纹 → 只有「另一个进程」那条挂**（说明为任务运行器存在的
  那一半确实被这条测试拦着）
- 短路掉记忆化 → 2 条「只构建一次」测试挂

### 可能被追问

- **为什么不直接换数据库？** 因为问题不是存储慢，是同一份数据在一次渲染里被重复解析
  几百遍。换数据库会让这个缺陷更难发现，而不是消失。
- **为什么 key 要有两半？** 去掉文件指纹只有「另一个进程」那条测试会挂——而那个进程
  是每天真实在跑的定时任务。
- **缓存的是什么？** 是**源读取**，不是返回的池；每个 getter 仍然构建并排序一份新
  数组，所以没有调用方能改到别人的列表。

## 故事二：五个公开页面会以构建时的样子永远冻住，而我没有拿构建清单当证据

**一句话**：这是在给另一件事搭生产对照时撞见的，而且它是正确性问题不是性能问题——
用户看到的症状不是「页面陈旧」，是**站内自相矛盾**。

### 发现

`/skills`、`/skills/[slug]`、`/knowledge`、`/knowledge/[slug]`、`/network` 是**唯一
五个没有 `export const dynamic = "force-dynamic"` 的公开页面**，其他每一个都有。于是
`next build` 会预渲染它们，而 `initialRevalidateSeconds` 是 `false`——**永不重新生成**。
41 条预渲染路由里，**38 条是这五个页面**。

### 关键：没有拿构建清单当证据

构建清单说它们是静态的，但那只是配置的自述。我做了一次真实的判别实验：

把生产服务器指向一份 `config/` 的**副本**（线上存储一个字节没写），副本里给一条已
发布技能的标题加了一个标记字符串，然后同时看四个面：

| 页面                | 命中标记 |
| ------------------- | -------- |
| `/workspace/skills` | ✓ 有     |
| `/skills`           | ✗ 0      |
| `/skills/[slug]`    | ✗ 0      |
| `/network`          | ✗ 0      |

**同一个进程、同一份数据，一个面更新了、另外三个没有**——这就排除了「数据本来就没变」
这个最容易的解释。

### 为什么它是正确性问题

用户看到的**不是一个陈旧的站，是一个自相矛盾的站**：`/search` 是动态的、**搜得到**
改过的标题，点进去的详情页却还是旧的。

而它砸在一个已经上线的功能上：技能 / 知识工作台编辑存在的**全部意义**就是运行时新建
和发布条目——在生产里，编辑会发布进一个永不更新的页面。

### 修复前先量代价，再交给决策者

这改变部署行为，所以我没有边测边改，而是把价签一起交出去：加 `force-dynamic` 之后
生产环境 **10–47 ms**（`/skills` 12 ms、`/knowledge` 11 ms、`/network` 39 ms、技能详情
47 ms），预渲染路由 **41 → 3**（剩下的是图标、icon 和 404）。

### 同一个探针反过来跑，就是它生效的证明

对着同一份带标记的副本，三个公开页从 **0 / 0 / 0** 命中变成 **2 / 4 / 3**，与工作台
一致；再用真实存储跑一次对照，内容正常、未知 slug 仍然 404。

### 两个我认为值得一提的收尾

1. **两个 `generateStaticParams` 一起删掉了。** `force-dynamic` 之后它们已经失效，
   留着会让下一个读代码的人以为这些页面是预渲染的，**也会在将来有人拿掉 `dynamic`
   时让它们重新静态化**。它们带出的两个没人用的 import 是 lint 抓到的，不是我看出来的。
2. **补了一道闸门**：`validate:deployment` 现在要求 `src/app` 下每个 `page.tsx` 都
   显式声明渲染模式（今天零例外）。用移除某个页面的 export 验证它会响——而且**先确认
   注入真的改到了文件**，才相信那次失败。

### 可能被追问

- **为什么之前没人发现？** 因为本地 `next dev` 永远是动态的。这个缺陷只在生产构建里
  存在，而在此之前没有人跑过生产构建。
- **为什么不用 ISR（revalidate）？** 可以，但这些页面的数据来自本地 JSON、写入是编辑
  动作触发的，没有一个自然的重验证周期；而实测动态渲染只要 10–47 ms，不值得为省这点
  时间引入一个陈旧窗口。

## 故事三：最慢的那条公开路由，其实是 dev server 在量它自己

**一句话**：一次全站计时扫描把某条路由报成 445 ms 的最慢公开路由，我花了一整轮去查，
**最后的结论是零代码改动**——而这一轮真正的产出是一个可复用的分诊方法。

### 起点是一个错误的前提

前一轮扫描报告 `/technologies` 是最慢的公开路由，445 ms。它的算术没错，**它的前提错了**：
那次扫描报的每一个数字都是 dev 模式的数字，而 **dev 模式的开销并不与生产开销成比例**。

### 先把归因坐实，再问值不值得修

我加了一个临时的 `renderLimit`：只渲染 63 张卡里的 N 张，但 **props 仍然把 63 条全部
序列化**——这样载荷恒定，只有渲染量在变。

| 渲染卡数 | 耗时   |
| -------- | ------ |
| 0        | 72 ms  |
| 16       | 163 ms |
| 32       | 271 ms |
| 48       | 377 ms |
| 63       | 436 ms |

完全线性，斜率 **5.8 ms 一张卡**。所以 436 ms 里 **364 ms 是逐卡 React 渲染**，数据加载
加 475 KB 载荷只占 72 ms。（仪器先自证：limit=0 渲染 0 张、limit=63 渲染 63 张。）

**生产下同一条斜率是 0.11 ms 一张卡，小 53 倍**；整条路由生产环境 **16 ms**。同样 63 张
卡、同样的载荷、两边都 `force-dynamic`——**相同的工作量，不同的运行模式**。

### 第三个「形状正确」的嫌疑犯，在写代码之前就死了

`UnbreakableTitle` 在一个逐卡的辅助函数里 `new Intl.Segmenter("zh-CN")`——这和当周修掉
的两个真实缺陷是同一个形状，看起来一定有问题。

拿真实标题做微基准：**构造一次 9.3 微秒，63 张卡合计 0.5 ms**。

缓存它会是一个看起来很对、实际一文不值的提交。**形状对不代表数量级对**——这是我这个
项目里反复付学费的一条。

### 真正的产出：dev/prod 倍率是一个分诊工具

测了 20 条按请求渲染的路由：

| 路由                    | dev → prod   | 倍率      |
| ----------------------- | ------------ | --------- |
| `/workspace`            | 189 → 107 ms | **1.8×**  |
| `/workspace/operations` | 202 → 90 ms  | 2.2×      |
| `/feed.xml`             | —            | 1.8×      |
| `/workspace/sources`    | —            | 19.6×     |
| `/technologies`         | 445 → 16 ms  | **24.7×** |

**倍率低，说明有东西可修；倍率高，说明 dev server 在量它自己。**

配套三条纪律：生产对照要建在**独立的 `distDir`**（`next build` 和 `next dev` 共用
`.next`，对着在跑的 dev server 做构建是记录在案的翻车方式）；预渲染路由的生产耗时是
「送一个文件」不是「一次渲染」，不可比；拆渲染成本时必须把载荷固定住，否则渲染和序列化
会一起动、两个都归不了因。

### 可能被追问

- **零改动的一轮，怎么算成果？** 它关掉了一个 backlog 项，并且防止了后面每一个人再对着
  dev 数字做优化。负结果只要是可复现的，就是结果。
- **那生产环境到底有没有慢的路由？** 最慢的公开路由是 32 ms，全站最慢是 126 ms——而那
  126 ms 正是故事一里修过的那条，它 6.1× 的倍率正确地说明剩下的成本是真实工作。

> server measuring itself”。

## 三个故事共同的那条线

如果只留一句话：**每一次，先出错的都是我的测量工具，而不是被测的代码。**

- 故事一：页面哈希里有时间戳，那个「有差异」在任何情况下都会有差异。
- 故事二：构建清单说它们是静态的——但那是配置的自述，不是行为的证据。
- 故事三：整条扫描的前提（dev 数字可以代表生产）是错的，而它的算术是对的。

所以这个项目里形成了一条固定做法，写进了 [`AGENTS.md`](../AGENTS.md) 的验证规则：
**在相信一个检查的干净结果之前，先注入一个缺陷，确认它会响。** 这一轮里那八个检测器
（引用块、竖线表格、ASCII 引号、弯引号、纯文本字段里的标记、用户名形状的发布方、不会
被 tokenize 的 `**`、落单反引号）就是逐个这样验证过的，8/8。
